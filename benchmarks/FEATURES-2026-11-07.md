# Three door/after-night features — pure modules, ready for UI wiring (2026-11-07)

Owner-approved: **walk-in at the door**, **guest memory**, **night-end report**.
Built as pure `Merit*` modules with suites. **Not wired yet**: no `<script>` tag,
no screen code, no i18n keys, so this commit changes nothing the app does. The UI
agent wires them after its rewrite.

| module | global | suite | what it does |
|---|---|---|---|
| `src/walk-in.js` | `MeritWalkIn` | `walk-in` | builds a walk-in's guest data and lists tables with room tonight |
| `src/guest-memory.js` | `MeritGuestMemory` | `guest-memory` | finds a person's history across the stored events (read-only) |
| `src/night-report.js` | `MeritNightReport` | `night-report` | builds one event's night-end figures and the rows of one summary sheet |

Each suite was written first and failed (the module was missing). Each one was
then shown to catch real bugs: three deliberate mutations per module, each made
the suite fail, then reverted. The mutations were: No Show seats counted as
taken, the VIP rule removed, pax forced to 1, the ambiguity check removed, every
outcome forced to NO_SHOW, walk-ins put into expected, `safeCell` dropped, and
planned seats used as tonight's seats. The suites load the modules straight into
a `vm` context, with no browser needed.

## 1. Walk-in at the door — `MeritWalkIn`

```js
const r = MeritWalkIn.buildWalkIn(event, { name, additionalGuests, invitedBy, vip, phone, notes }, nowISO());
// r.refused: "NO_EVENT" | "HISTORICAL" | "NAME_REQUIRED"
// r.data: the `data` for saveGuestRecord(event, null, data)
// r.alreadyListed: [{ guestId, name, pax }] (this name is already on the list)
// r.then: { arrival: "Checked In", source: "walk-in" }
```

The UI should do these steps, in this order:

1. Call `canMutate(event, "edit guest records")`.
2. If `alreadyListed` is not empty, show those guests first. The person may
   just need checking in. The module never merges records.
3. Create the record: `const { guest } = saveGuestRecord(event, null, r.data)`.
   Use the existing writer. It sets the id, "Not Arrived" and `assignment: null`.
4. Check the guest in: `setArrival(event, guest, "Checked In", "walk-in")`. This
   is the one arrival writer, and it writes the audit entry. The module never
   writes `arrivalStatus` or `checkedInAt` itself; `domain-writers` would catch
   it if it did.
5. Call `touchEvent(event); render();`.

Name rules:

- `"Ali Kaya +2"` gives ONE record with pax 3. This is the guest dialog's
  `parseCompactName` rule (`MeritWalkIn.parseName`).
- An explicit companion count wins over a typed `+N`.
- `walkIn: true` and `walkInAt` (the moment the door registered the person) are
  the only new fields.

```js
const s = MeritWalkIn.suggestSeats(event, guest.pax, { vip: guest.vip });
// s.refused: "NO_EVENT" | "HISTORICAL"
// s.options: [{ tableId, number, zone, vipTable, capacity, liveFree, plannedFree,
//               freedByNoShow, assignable, seats }]   (best first)
// s.blocked: [{ tableId, number, why: NO_SEATS|UNAVAILABLE|FROZEN|VIP_ONLY|NOT_ENOUGH_SEATS }]
// s.mutated: false
```

- **Tonight's room.** `liveFree` counts seats with nobody in them tonight
  (`MeritOccupancy.liveUsedIndexes`). Seats left by a No Show count as free.
- **Finding for the wiring pass.** The existing seat writer,
  `assignGuestToTable` → `assignGuestGroup` in app-v8.js, counts **planned**
  seats (`occupiedSeatIndexes`). A No Show still holds their planned seat, so a
  table that only fits because of a No Show can NOT be applied through the
  writer. Taking that seat would mean touching the No Show's `guest.assignment`,
  which the product forbids.
  - The option says this: `assignable: false`, with `freedByNoShow` > 0.
  - Only an `assignable: true` option gets an Apply button:
    `assignGuestToTable(guest.id, opt.tableId)`. Do this after Apply, never
    automatically.
  - **A No Show's freed seat, with a confirmation (owner decision 2026-11-08,
    built).** A non-assignable option whose free seats include a No Show's is
    `livePlaceable: true`, with `liveSeats` (the No Show's freed seats first,
    then plan-free ones, the whole party) and `noShows` (`{guestId, name}`, whose
    place it is). Kapı shows "Gelmeyenin yerine oturt"; it asks "Gelmeyen X'in
    yeri — buraya oturtulsun mu?" (the product's `ask()` dialog; No = nothing),
    re-checks the room after the answer, and on Yes calls
    `MeritOccupancy.placeLive(event, guest, {tableId, seats}, {confirmed: true, now, paxOf})`
    — the ONE writer of `guest.livePlacement = {tableId, seats, noShowGuestIds, at}`
    (the walk-in suite fails on any other write site in `src/`). It refuses
    without `confirmed`, on a historical event, for a guest that is not a
    checked-in walk-in, for a guest with a planned seat, for a seat used tonight,
    for a seat count other than the party's pax, and for plan-free seats only
    (those go through the assignment writer). `liveUsedIndexes` counts a
    placement (only on a guest with no `assignment`), so the door, the live
    canvas and the next walk-in see the seats used.
  - **What does NOT change.** The No Show keeps `guest.assignment` and arrival
    status; `occupiedSeatIndexes`, `tableAssignedPax` and every planned figure
    ignore the placement. **How a walk-in appears in the reports:** GUEST LIST
    lists the walk-in record (pax, Confirmed, VIP, host) with an EMPTY table and
    seat column, and UNASSIGNED lists them — both read `guest.assignment`, which
    a live placement never writes; TABLE PLAN still shows the No Show in the
    planned seat. The night-end report lists them under walk-ins and counts
    the seats as held tonight (`liveUsedIndexes`). The Kapı room picture counts
    planned/arrived from assignments only, so a live-placed walk-in is not in
    its table's figure.
  - **Known, not handled (deliberately):** if the No Show later arrives, the
    seat is used twice tonight — nobody is moved automatically; the operator
    decides. A later plan-free assignment at that table could pick a plan-free
    seat a placement also uses (placements prefer the No Show's seats to keep
    this rare). There is no undo button for a placement yet.
- **Order.** Assignable options come first. For a VIP or VVIP guest, VIP tables
  come next. Then the tightest fit, then the table number.
- **Rules.** VIP tables (zone or number containing VIP) are offered only to VIP
  and VVIP guests. Unavailable, frozen and seatless tables are never offered.
  The party is never split.

## 2. Guest memory — `MeritGuestMemory`

```js
const m = MeritGuestMemory.recall(state.events, guest, { exceptEventId: event.id });
// { none, person: { name, phone },
//   history: [{ eventId, eventName, date, outcome: "CAME"|"NO_SHOW"|"NOT_RECORDED"|"UPCOMING",
//               table, pax, vip, notes, host, walkIn, matchedBy: "name+phone"|"name" }],  // newest first
//   summary: { events, came, noShow, notRecorded, upcoming, vipMarks, hosts, tables } }
// or { ambiguous: true, people: [{ name, phoneEnding, eventIds }], history: [] }
```

- **Matching.** It uses the existing matcher, `MeritAssistantTools.findPerson`.
  That matcher folds names (ı/i, case), so "AHMET YILMAZ" finds "Ahmet Yılmaz".
  A phone whose last 7 digits disagree makes a different person. Groups with the
  same name are joined only when their phones agree under that same last-7 rule.
  For example, "+90 532…" and "0532…" are one person.
- **Ambiguous.** The same name under two phones, asked about without a phone,
  returns `ambiguous`. Show both candidates and let a person choose. The module
  never merges them.
- **Outcomes.** Only "Checked In" counts as came. A past event with no arrival
  record is NOT_RECORDED, never "came" or "no show".
- **Read-only.** `recall` only reads. A UI that offers "use last time's note"
  should copy it as a person's act through `saveGuestRecord`.
- **Where to call it.** In the guest dialog or the door row, for the open
  guest. It is cheap: one pass over the events.

## 3. Night-end report — `MeritNightReport`

```js
const r = MeritNightReport.build(event);   // plain data, read-only; works on a Completed event
// r.people: { expected, arrived, noShow, notArrived, walkIns, inRoom }   (pax)
// r.hosts: [{ host | null, expected, arrived, noShow, walkIns, rate }]   (rate = arrived/expected, null when nothing expected)
// r.firstArrival / r.lastArrival: ISO | null   r.untimedArrivals: records checked in with no moment
// r.noShows: [{ guestId, name, pax, host, table }]   r.walkIns: [... , at, arrival]
// r.seats: { capacity, planned, heldTonight, seatedArrived, empty, freedByNoShow, arrivedUnseated }
const rows = MeritNightReport.summaryRows(r, (key) => t("night." + key));  // array of arrays, one sheet
```

- **What the figures mean.**
  - `expected` and the per-host `rate` never include walk-ins.
  - `inRoom` = everyone checked in, walk-ins included.
  - Hosts are grouped by `MeritGuestGroups.hosts` (folded names). Guests with no
    host get their own row with `host: null`.
  - `seats.planned` keeps a No Show's seats. `heldTonight` frees them. `empty`
    is capacity minus the seats of people who actually came.
- **Labels.** The keys are in `MeritNightReport.DEFAULT_LABELS`; the English
  defaults are uppercase, like the existing workbook. A key the label function
  returns empty for falls back to its default.
- **Formula safety.** Every cell goes through `MeritNightReport.safeCell`. Any
  text starting with = + - @ (or tab/CR) gets a leading `'`, the same as
  `exportJunketReport`.
- **Export wiring.** Add a separate export, e.g. a Reports button "Gece sonu
  raporu" next to the junket report:
  ```js
  const ws = XLSX.utils.aoa_to_sheet(rows);
  XLSX.utils.book_append_sheet(wb, ws, "NIGHT END");
  XLSX.writeFile(wb, …);
  ```
  - Do **not** add this sheet to the TABLE PLAN / GUEST LIST / UNASSIGNED
    workbook. That workbook is regression-guarded (`xlsx-contract`).
  - The module builds no workbook itself, and its suite fails if it ever names
    those sheets.
