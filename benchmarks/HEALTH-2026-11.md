# Pre-Windows health check — 2026-11-07

Does the product survive a real gala night? Measured on branch
`claude/merit-concept3-plan-intelligence-rebirth`, Chromium headless
(Playwright), 1920×1080, 4 cores / 16 GB.

**Load.** Run 1 was on an idle machine (load average ~1, the suite itself).
From 10:01 a LoRA training job (`training/vlm_lora.py train`, ~2.7 cores,
10 GB) held the CPU; run 2 and every run after it were measured under it
(load average 5.8–6.3 on 4 cores). Under load the numbers are upper bounds.

## 1. Big event — `gala-night-scale` (slow)

1,000 guest records / 1,500 people (+2 on every tenth record, +1 on three in
ten) from a generated `.xlsx` through the real import wizard; 100 tables of 18
from the Floor Plan's add panel (1,800 seats); 950 records seated through
`assignGuestToTable` → `MeritSeatAssignment`, 50 left unseated; 300 checked in
by clicking their row's button on Live; the workbook exported five times and
read back.

Timed in the page (`performance.now()`, forced layout flush inside the timed
region); export is wall clock from the click to the file.

| operation | n | idle: median / p95 / max (ms) | under load, run 2 | under load, run 3 | budget (p95) |
|---|---|---|---|---|---|
| guest list render (Guests tab, 1,000 records) | 20 | 14.4 / 19.5 / 22.6 | 15.4 / 22.7 / 28.5 | 13.6 / 34.9 / 35.6 | 70 |
| search keystroke, Guests | 40 | 8.8 / 17.4 / 28.9 | 6.7 / 14.3 / 15.5 | 8.2 / 21.2 / 71.8 | 45 |
| search keystroke, door (Live) | 40 | 6.8 / 13.1 / 14.5 | 7.8 / 13.9 / 17.0 | 6.5 / 22.1 / 23.6 | 45 |
| seating assign (writer + Seating render) | 950 | 48.8 / 79.2 / 131.2 | 80.5 / 138.3 / 240.2 | 78.1 / 135.1 / 252.7 | 280 |
| check-in click (Live row button) | 300 | 14.9 / 18.5 / 55.7 | 17.0 / 30.4 / 149.0 | 15.1 / 28.7 / 77.9 | 65 |
| report export (TABLE PLAN / GUEST LIST / UNASSIGNED) | 5 | 110 / 115 / 115 | 127 / 137 / 137 | 124 / 181 / 181 | 365 |
| import, file chosen → 1,000 records (wall clock incl. wizard clicks) | 1 | 987–1,011 | 969 | 951 | — |

Budget rule (as `benchmarks/perf/BUDGETS.json`): max(2 × worst observed p95,
worst p95 + 15 ms), rounded up to 5 ms, over all three runs. Headroom is
therefore 2× the slowest (loaded) run. Proved to bite: a 200 ms delay in `assignGuestToTable` failed the
seating budget as it then stood (p95 293 ms against 160; the budget is 280 now,
so this gate catches roughly a doubling, not a smaller slowdown), and
`liveStats` counting records instead of people failed the recount check.

Correctness checked at the same size: 1,000 rows → 1,000 records (a +N party is
one record, pax = 1 + additional); no seat given twice or past capacity; the
300 check-ins changed no planned seat or planning status; the door's figures,
in the module and on screen, equal a recount; the workbook has every record on
GUEST LIST, exactly the 50 unseated on UNASSIGNED, one `GUEST OF` seat per
companion and every table on TABLE PLAN.

## 2. Crash

| case | where it is guarded | result |
|---|---|---|
| tab closed mid-edit (write never lands) | `resilience-records` §4 | existing, covered |
| tab closed the instant after a door check-in, reload, reload again | `long-night-door` part 2 (new) | PASS — arrival, moment, planned seat and audit entry there once; second reload applies nothing twice; Enter on the same guest says "already checked in" and changes nothing |
| storage full → Turkish notice, previous data intact | `resilience-storage` | existing, covered ("KAYDEDİLMİYOR", backup beside it, no half record) |
| corrupt IndexedDB / localStorage record → boots and says what it could not read | `resilience-records`, `resilience-storage`, `offline-recovery` | existing, covered |

Proved to bite: with the close-time snapshot listeners removed, part 2 lost the
check-in and the same guest could be checked in a second time.

## 4. Long night — `long-night-door` (slow)

600 records / 1,000 people on 50 tables, all seated. 3,000 door operations
through the Live screen's own controls, seeded (2026-11-07): check-in button
816, search + Enter 276, No Show 290, Recent's Undo 975, take back from the
row 643 → 2,956 real changes. Heap after a forced GC and the renderer's DOM
counters sampled after a 250-operation warm-up and every 500 operations.

| measure | after warm-up | after 3,000 | growth | bound |
|---|---|---|---|---|
| JS heap after GC | 12.07 MB | 14.52 MB | +2.45 MB (incl. ~2,700 audit entries) | 8 MB |
| JS event listeners | 582 | 581 | −1 | +50 |
| DOM nodes | 5,301 | 5,295 | −6 | +500 |
| documents | 2 | 2 | 0 | 0 |
| one door operation | | | median 14–17 ms, p95 33–40 ms | — |

Every guest's arrival equals what the operations said; 2,956 changes ↔ 2,956
audit entries; figures (module and screen) equal the recount; every planned
seat and planning status identical before and after (No Show keeps the seat;
tonight's used seats exclude No Shows). Proved to bite: a listener added per
Live render failed the listener, node and heap bounds.

## Bugs found

None in this pass: every case either passed against the current code or was
already guarded by an existing suite. Each new check was proved to fail on a
deliberate mutation before being trusted.
